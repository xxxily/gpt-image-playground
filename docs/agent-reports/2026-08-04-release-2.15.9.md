## 问题与解决

| 问题 | 解决办法 | 剩余风险 |
| ---- | -------- | -------- |
| MIME 通配与具体类型可能形成无效组合 | 选择具体 MIME 自动移除 `image/*`，选择通配自动清空具体类型，并始终保留至少一种合法类型 | 无已知交互风险 |
| 用户补充要求元数据可能与双语 prompt 不一致 | 配方 helper 同步添加或清理 `{{user_instruction}}`，关闭补充要求时同时清理 token | 高级 JSON 仍必须经过同一 schema 校验 |
| URL 语法校验无法阻止 DNS rebinding 或重定向 SSRF | 发布时逐跳解析全部地址、拒绝任一非公网地址，并用 Node HTTPS `lookup` 固定连接到已校验 IP | 带敏感签名参数或依赖私网回源的外部地址应改用托管媒体 |
| 单请求超时不能约束慢 DNS 与多跳累计时长 | 使用同一 deadline 覆盖 DNS、重定向、下载和 Sharp metadata 阶段 | CPU 极端繁忙时不是硬实时中止，但响应体、尺寸和像素均有上限 |
| 161 的官方 Debian archive 连续两次不可达 | 两次失败均发生在 129 上传和切换前；在 detached 部署 worktree 中临时切换到已验证可达的阿里云 Debian archive | 正式构建脚本仍缺 archive 镜像回退与有限重试，应后续单独合入 |
| 阿里云 HTTPS archive 在最小 Debian 镜像中缺少 CA 引导 | 一次性构建容器改用同镜像 HTTP archive，继续由 Debian Release/包签名校验完整性；安装 CA 后后续下载恢复 HTTPS | 临时辅助改动未进入 `master` 或 `v2.15.9` tag，已在日志中披露 |
| `node-gyp` 可能再次访问 Node headers | detached worktree 临时设置 `npm_config_nodedir`，复用缓存 Node `20.20.2` 自带 headers | 建议把已验证方式正式纳入构建脚本 |
| 本机直接下载 `latest.json` 遇到 release-assets TLS 断开 | 使用 GitHub Release API 核验 `latest.json` 已发布且大小为 5,670 bytes；CI 的 updater 签名和 Publish Release job 已成功 | 未在本机再次解析文件内容；客户端安装级 updater 验收仍待补做 |

## 明确跳过与后续建议

- 未补齐 24 个真实生成、授权和人工核验的案例资产；默认媒体继续明确标识为演示占位。
- 未执行至少 5 名非专业用户的 30/60 秒可用性测试。
- 未在 macOS、Windows、Linux 或 Android 真机安装 Release 资产；CI 成功不能替代安装级验收。
- 漏斗当前仍使用单实例 SQLite；多实例部署前应迁移到集中式存储或导出链路。
- 后续应把 Debian archive 镜像回退、有限重试和 `npm_config_nodedir` 正式合入 `scripts/build-129-runtime-docker.sh`。
- 后续随 Tauri / plist / Wayland 依赖兼容升级处理 `quick-xml 0.39.2` RustSec 风险，并先验证项目 Rust MSRV 与全平台构建。
