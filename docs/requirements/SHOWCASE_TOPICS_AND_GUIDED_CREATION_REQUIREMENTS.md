# 专题案例与引导式创作能力需求文档

## 1. 核心结论

GPT Image Playground 当前以专业工作台为中心，功能完整，但用户必须先理解提示词、模型、供应商、源图片顺序、尺寸、质量和输出参数，才能知道“它能做什么”和“第一步该怎么做”。对于第一次接触 AI 图片生成或编辑的用户，这种信息架构把专业能力直接暴露在最前面，也把学习成本提前到了价值感知之前。

本需求建议新增一套独立的 **专题案例与引导式创作能力**：

1. 在保留当前专业工作台为首屏主体的前提下，于工作台下方提供“热门专题 / 从案例开始”内容区，并在全局功能菜单提供稳定入口。
2. 每个专题围绕一个明确用户任务组织，例如“老照片修复”“虚拟试衣间”“创意风格化”，而不是围绕模型名或技术参数组织。
3. 每个专题包含多个真实案例，展示输入、输出、效果差异、适用范围、输入要求和注意事项。
4. 用户选择案例后，通过一个轻量引导流程准备自己的图片和个性化要求，再将经过校验的“复现配方”载入现有专业工作台。
5. 载入配方默认只准备工作台，不自动发起真实生成，不覆盖用户密钥或服务地址，也不隐藏将要使用的提示词和参数。
6. 管理员通过现有后台身份、权限和审计体系管理专题、案例、媒体、配方、排序、上下线、定时发布和多语言内容。
7. 专题是独立内容领域，不直接塞入现有 Promo 展示组。Promo 继续负责“在什么展示位向谁展示什么入口”，专题负责“案例内容、复现配方和引导流程”；两者可以互相引用。
8. Web、Tauri 桌面和 Tauri Android 共享内容契约。动态内容优先读取远端已发布目录，失败时回退到最近成功缓存，再回退到随应用内置的默认专题。

建议用户可见名称统一使用 **“专题”** 和 **“案例”**；代码与数据领域可使用 `showcase` 前缀，避免与 Promo、提示词模板、素材灵感网站和用户历史混淆。

## 2. 背景与问题

### 2.1 当前体验偏向“先学工具，再获得结果”

当前首页直接渲染工作台，没有独立营销首页或新手首页（`src/app/page.tsx:1-5`）。主工作台同时承载生成、编辑、图生文、视频、批量、历史、素材和工作空间等能力，专业用户能够高效使用，但新手常见路径是：

1. 先看到大量专业控件；
2. 不确定应该选择什么模式、模型和尺寸；
3. 不知道是否需要上传图片、上传几张、顺序有什么含义；
4. 不知道提示词要写到什么程度；
5. 在尚未看到产品价值前先进入配置和学习阶段；
6. 最终把产品理解为“又一个需要自己研究提示词的生成界面”。

### 2.2 产品能力已经存在，但缺少面向任务的表达层

项目已经具备大量可以支撑专题能力的底层基础：

| 已有能力           | 当前现状                                                                                                                                           | 对专题能力的价值                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 专业工作台         | 主区由生成/编辑与输出双栏、任务、历史组成（`src/features/workbench/page/workbench-shell.tsx:340-394`）                                             | 专题不需要重做生成引擎，只需要把正确状态安全载入工作台         |
| 提示词模板         | 模板当前只有分类、名称、描述和 prompt（`src/types/prompt-template.ts:1-22`），默认模板由静态目录提供（`src/lib/default-prompt-templates.ts:7-90`） | 可复用部分提示词内容，但不足以表达输入角色、模型能力和完整参数 |
| 批量改图预设       | 已有老照片修复、风格迁移、增强、背景重绘等预设（`src/lib/batch-image-edit.ts:12-12`、`src/lib/batch-image-edit.ts:147-160`）                       | 可作为首批默认专题提示词和能力验证的来源                       |
| 场景尺寸选择       | 已有场景化比例与模型适配能力                                                                                                                       | 复现配方可引用 `scenarioId`，避免后台硬编码所有模型尺寸        |
| 表单状态控制       | `EditingFormHandle` 已支持读取、替换和追加提示词（`src/components/editing-form/editing-form.types.ts:146-155`）                                    | 专题配方可以通过受控适配器载入，不必模拟 DOM 操作              |
| 素材与灵感工作区   | 浮动菜单和左右分区已支持工作空间、素材库与灵感库（`src/components/app-feature-menu.tsx:15-181`）                                                   | 可复用入口、Drawer、分区和移动端降级模式                       |
| 展示位与 Promo     | 已有公开展示位、展示组、素材、约束、分享 Profile 和后台管理（`src/lib/server/schema.ts:130-266`）                                                  | 可用于给专题导流，但 Promo 数据模型不承担专题正文与配方        |
| 后台体系           | `/admin` 已有 owner/admin/viewer、会话保护、审计和导航（`src/components/admin/admin-shell.tsx:26-35`、`src/app/admin/(shell)/layout.tsx:6-14`）    | 专题管理应直接接入，而不是新建第二套管理员体系                 |
| Web/Tauri 远端内容 | Promo 已能在 Web 读取同源 API、Tauri 读取配置的远端地址，并带超时和缓存回退（`src/components/promo-slot.tsx:110-183`）                             | 专题目录可复用同类公共内容服务与降级策略                       |

现有能力主要回答“怎么操作”，没有形成一个面向小白的内容层来回答：

- 这个工具能帮我完成哪些具体任务？
- 我需要准备什么？
- 输入和结果大致是什么样？
- 哪些结果只是示例，哪些效果可以较稳定复现？
- 点击后系统会替我配置什么，又有哪些内容需要我确认？
- 如果当前模型不支持，下一步应该怎么办？

### 2.3 仅增加更多提示词模板不能解决问题

提示词模板适合熟悉工作台的用户快速填写 prompt，但专题案例还必须表达：

- 任务模式：文生图、图片编辑、图生文、图生视频等；
- 输入槽位：需要几张图片，每张图片扮演什么角色；
- 源图片顺序：例如试衣场景中的人物图、服装图；
- 模型能力：是否必须支持编辑、蒙版、多参考图或自定义尺寸；
- 输出参数：比例、质量、背景、格式和数量；
- 示例解释：为什么会得到这个效果，哪些细节可能不稳定；
- 用户准备步骤：上传、裁剪、替换、追加个性化要求；
- 版本与兼容：后台修改配方后，旧案例和旧链接如何继续工作；
- 发布与审核：草稿不能直接泄漏到公开用户端。

因此，专题不应退化为“带封面的提示词模板分类”。

## 3. 产品定位与术语

### 3.1 专题（Topic / Showcase Topic）

围绕一个用户任务组织的内容集合。专题负责解释任务价值、适用人群、输入要求、可获得的结果、限制和多个案例。

示例：

- 老照片修复
- 虚拟试衣间
- 创意风格化
- 电商商品场景图
- 图片清晰增强
- 人像头像与形象照

### 3.2 案例（Case / Showcase Case）

专题下一个可理解、可复现的具体示例。案例至少包含输入示意、输出结果、效果说明、复现配方、输入槽位和适用条件。

一个专题可以有多个案例，例如“老照片修复”下可以有：

- 去划痕与污渍；
- 降噪与清晰增强；
- 褪色修复；
- 黑白照片自然上色；
- 低分辨率人物照片修复。

### 3.3 复现配方（Recipe）

由后台管理、经过版本化和白名单校验、可以载入工作台的一组结构化配置。它不是任意脚本，也不是一段不可见的魔法 prompt。

配方可以描述：

- 任务模式；
- 默认提示词及其应用方式；
- 输入图片槽位和排序；
- 所需模型能力；
- 推荐模型但不强制供应商；
- 场景尺寸或输出比例；
- 质量、格式、背景、数量等允许的工作台参数；
- 可选的用户补充要求；
- 配方版本与兼容策略。

配方不得包含：

- API Key、Token、密码；
- 用户或管理员的供应商凭证；
- 任意 JavaScript、HTML 事件或可执行代码；
- 未受控的服务器请求配置；
- 用户本地文件路径；
- 大体积 Blob、base64 图片或完整图片字节；
- 绕过 URL 安全规则的私网地址。

### 3.4 专题目录（Catalog）

公开端在某一时间可见的已发布专题集合。目录带 `schemaVersion`、`catalogRevision` 和生成时间，供 Web、桌面、移动端缓存与兼容判断。

### 3.5 用户作品

用户根据专题生成的结果仍然属于现有任务与历史体系。P0 不建设公开作品社区；只在任务和历史元数据中记录可选的专题来源归因。

## 4. 目标

### 4.1 用户目标

1. 用户无需理解模型名和高级参数，就能通过真实案例快速知道产品能做什么。
2. 用户在 60 秒内可以从首页找到一个专题、理解输入要求并进入自己的素材准备流程。
3. 用户点击案例后，可以看清系统将应用的提示词和参数，而不是盲目执行。
4. 用户可以用自己的图片复现案例，同时保留修改提示词、切换模型和调整参数的专业能力。
5. 当当前配置不支持案例时，系统给出具体原因和下一步动作，而不是在提交后才报错。
6. 专业用户可以跳过引导，直接把配方载入工作台或展开完整参数。

### 4.2 产品目标

1. 把“功能列表”升级为“任务结果展示”，降低首次价值感知门槛。
2. 建立从内容发现到真实生成的可观测漏斗，判断哪些能力真正吸引用户。
3. 允许运营人员不发版即可调整专题、案例、排序和发布节奏。
4. 让默认专题同时成为产品演示、用户教育、模型能力验证和推广落地内容。
5. 保持专业工作台是核心生产工具，不把应用改造成只适合浏览的营销网站。

### 4.3 管理目标

1. 管理员可以创建、复制、预览、发布、下线和归档专题。
2. 管理员可以维护案例媒体、输入要求、提示词、配方、模型能力、排序和多语言内容。
3. 发布动作必须原子化；未完成的草稿不会影响线上已发布版本。
4. 所有管理写操作进入现有审计体系，并遵循 owner/admin/viewer 权限边界。
5. 默认专题可被定制或下线，同时保留恢复内置版本或复制为自定义专题的能力。

## 5. 非目标

P0 不包含以下能力：

- 不建设公开用户作品社区、点赞、评论、关注或排行榜。
- 不要求用户登录后才能浏览专题或使用案例。
- 不让专题详情取代专业工作台，也不增加落地页式大 Hero、装饰性光斑或与工具无关的首屏营销内容。
- 不在用户打开专题、选择案例或载入配方时自动产生 API 费用。
- 不根据案例静默保存或替换用户的供应商、API Key、Base URL 和代理设置。
- 不保证示例结果可像素级复刻；案例展示代表能力方向，不是结果承诺。
- 不允许管理员通过配方注入任意供应商请求参数、脚本或未审核 HTML。
- 不把专题内容直接存入 `promo_items`、提示词模板或素材灵感网站配置。
- 不在 P0 自动下载第三方网站的案例图片，也不绕过版权、登录、CSP 或反盗链规则。
- 不在 P0 提供复杂的可视化工作流编排器；配方编辑器只覆盖已允许的工作台状态。
- 不在 P0 为后台内容建设多人实时协同编辑。

## 6. 目标用户与核心任务

| 用户类型             | 典型状态                              | 需要解决的问题                       | 专题价值                               |
| -------------------- | ------------------------------------- | ------------------------------------ | -------------------------------------- |
| 第一次使用的小白     | 不理解模型和提示词                    | “我能用它做什么，应该从哪里开始？”   | 通过案例先看到价值，再逐步准备输入     |
| 有明确需求的普通用户 | 知道想修照片或换衣服，但不会写 prompt | “有没有现成流程让我跟着做？”         | 提供输入槽位、默认配方和可编辑说明     |
| 内容创作者与运营     | 需要快速批量尝试创意                  | “哪些场景和风格值得尝试？”           | 用专题发现新能力，再进入专业工作台微调 |
| 专业设计或 AI 用户   | 熟悉参数，重视效率                    | “能否跳过说明直接复用配方？”         | 一键载入并保留所有高级控制能力         |
| 管理员或运营人员     | 负责案例质量和内容更新                | “如何不发版就调整案例和默认工作流？” | 通过后台草稿、预览、发布和审计完成运营 |

核心 Jobs-to-be-Done：

> 当我有一个具体的图片任务，但不知道该选什么模型、如何组织图片和提示词时，我希望先看到可信案例和准备要求，再用自己的素材快速开始，同时仍然可以修改所有关键设置。

## 7. 产品设计原则

1. **结果先于参数**：先展示用户任务与结果，再解释模型和高级参数。
2. **渐进式披露**：默认路径只展示完成当前案例必需的信息，专业参数随时可展开。
3. **透明可控**：提示词、输入顺序和将要修改的参数必须可查看；不静默自动提交。
4. **能力驱动而非供应商驱动**：配方优先声明“需要编辑、多参考图、蒙版”等能力，避免与某个供应商永久绑定。
5. **内容与执行分离**：专题负责展示和引导，工作台继续负责真实生成、错误、任务、历史和费用。
6. **发布版本稳定**：公开用户读取发布快照，后台草稿编辑不直接污染线上内容。
7. **跨端可降级**：远端内容不可用时仍能查看内置专题并使用本地工作台。
8. **不阻塞首屏工具**：专题加载失败、变慢或数据异常，不能影响生成、编辑、历史、分享和同步。
9. **示例不等于承诺**：明确展示案例使用条件、可能差异和模型限制。
10. **默认内容少而精**：首发专题控制数量和质量，避免堆出一个无人维护的模板市场。

## 8. 信息架构

### 8.1 页面与入口

建议 P0 提供以下入口：

| 入口           | 位置                                   | 作用                                            |
| -------------- | -------------------------------------- | ----------------------------------------------- |
| 首页专题区     | 主工作台下方、任务追踪之后、历史区之前 | 让新用户自然发现高价值能力，不改变首屏工具定位  |
| 全局功能菜单   | 与工作空间、素材库、灵感库同级         | 为已滚动或回访用户提供稳定入口                  |
| 专题中心       | 静态路由壳 `/topics`                   | 浏览、搜索、筛选全部专题                        |
| 专题详情       | `/topics?topic=<slug>`                 | 展示专题说明和案例集合，兼容 Tauri 静态导出     |
| 案例定位       | `/topics?topic=<slug>&case=<caseSlug>` | 打开指定案例，便于分享、短链和 Promo 引流       |
| 工作台来源提示 | 配方载入后的编辑区                     | 显示“来自某专题 / 某案例”，可返回案例或清除来源 |

不建议 P0 把任意后台 slug 设计为只能依赖 Node 动态路由的 `/topics/[slug]`。桌面构建使用 `output: 'export'`（`next.config.ts:3-13`），后台又要求运行期新增专题，因此统一的静态页面壳加 query 参数更稳妥。Web SEO 友好的服务端专题落地页可以作为后续独立增强，但不能成为桌面访问专题的前提。

### 8.2 首页专题区位置

当前主工作台在生成/编辑与输出双栏之后依次呈现 `TaskTracker`、历史上方 Promo 和 `HistoryPanel`（`src/features/workbench/page/workbench-shell.tsx:347-392`）。建议新增顺序为：

```text
生成 / 编辑 + 输出
        ↓
任务追踪
        ↓
热门专题 / 从案例开始
        ↓
现有 history_top_banner Promo
        ↓
历史记录
```

理由：

- 不把专题变成首屏 Hero，保留工具本体优先级；
- 专题不会被长历史列表压到页面最底部；
- 用户完成一次任务后也能看到“下一步还能做什么”；
- 现有 Promo 仍然保留独立展示职责。

### 8.3 专题中心结构

专题中心包含：

- 推荐专题；
- 最新上线；
- 按任务类型分类；
- 按输入类型筛选：无需图片、单图、多图、蒙版；
- 按能力筛选：修复、风格化、商品、人像、营销、空间；
- 搜索专题标题、摘要、标签和案例标题；
- “适合第一次体验”标识；
- “当前配置可直接使用 / 需要配置兼容模型”状态。

P0 不做个性化推荐。默认排序由后台 `featured`、`sortOrder`、发布时间决定。

## 9. 首页专题区需求

### 9.1 展示形态

首页默认展示 6 至 8 个专题卡片，桌面端为响应式网格或横向可滚动卡片，移动端优先使用两列卡片或单列紧凑卡片。卡片至少包含：

- 封面或代表性前后对比缩略图；
- 专题标题；
- 一句话结果描述；
- 输入要求，例如“需要 1 张照片”“需要人物图 + 服装图”；
- 难度或上手标签，例如“适合新手”；
- 案例数量；
- “查看案例”操作；
- 当前设备/模型不可用时的非阻断提示。

卡片不能依赖 hover 才显示关键信息和主要操作。

### 9.2 加载与降级

- 首页专题请求不得阻塞工作台首屏交互。
- 专题区进入视口或浏览器空闲后再加载远端目录。
- 远端请求超时后显示最近成功缓存或内置默认专题。
- 所有来源都不可用时，专题区可以整体隐藏或显示轻量重试提示，但不占用大面积空白。
- 骨架屏尺寸必须稳定，避免专题加载导致历史区大幅跳动。
- 首页只返回卡片摘要，不下载详情正文和全部案例大图。

### 9.3 用户行为

- 点击卡片进入专题详情，不直接生成。
- 可通过“查看全部专题”进入专题中心。
- 可记录匿名的展示和点击事件，但不记录用户图片、prompt、API Key 或本地路径。

## 10. 专题详情需求

### 10.1 页面内容

专题详情至少包含：

1. 标题与简短结果说明；
2. 代表性封面或前后对比；
3. “这个专题能做什么”；
4. “你需要准备什么”；
5. 适用场景与不适用场景；
6. 推荐输入质量，例如正面、光线、遮挡、分辨率；
7. 案例集合；
8. 常见问题与结果差异说明；
9. 相关专题；
10. “选择一个案例开始”主操作。

### 10.2 详情布局

- 保持 utilitarian 工具风格，不制作大型营销 Hero。
- 桌面端可使用左侧说明、右侧案例预览，或上方摘要、下方案例网格。
- 移动端按“摘要 → 准备要求 → 案例 → 注意事项”纵向排列。
- 标题、按钮、标签和说明全部进入现有 i18n 体系；后台内容按语言返回。
- 支持浅色/深色主题、键盘导航、触摸操作和安全区。

### 10.3 案例卡片

案例卡片至少显示：

- 输入缩略图；
- 输出缩略图；
- 案例标题和简短说明；
- 所需图片数量和角色；
- 推荐能力标签；
- “跟着创建”按钮；
- “查看配方”次要操作。

前后对比组件应支持：

- 并排对比；
- 滑杆对比；
- 移动端点击切换；
- 明确标记“输入示例”“AI 结果示例”；
- 图片加载失败时显示 alt 和占位，不让页面崩溃；
- 不以过度压缩、不同裁剪或误导性光照制造虚假效果差异。

## 11. 引导式创作流程

### 11.1 总体流程

```text
选择专题
  → 选择案例
  → 查看效果与限制
  → 准备自己的输入素材
  → 补充个性化要求
  → 校验当前模型与参数
  → 预览将应用的配方
  → 载入专业工作台
  → 用户主动点击生成
```

### 11.2 引导容器

P0 建议使用响应式 Dialog / Drawer：

- 桌面端可使用中等宽度 Dialog 或右侧非阻断面板；
- 移动端使用全屏 Drawer；
- 不使用 `window.alert`、`window.prompt`、`window.confirm`；
- 用户可以随时退出，退出不修改工作台状态；
- 最后一步确认后才原子化应用配方。

### 11.3 输入槽位

配方必须显式声明输入槽位，而不是只声明“共需要 N 张图”。每个槽位包含：

- 稳定 `id`；
- 用户可见名称；
- 角色说明；
- 是否必填；
- 最小和最大数量；
- 接受的媒体类型；
- 推荐构图、分辨率和背景；
- 在工作台源图中的顺序；
- 是否允许从历史、素材库、粘贴或本地文件选择；
- 是否允许使用专题公开参考资产。

示例：虚拟试衣案例可以定义：

| 顺序 | 槽位     | 要求                                       |
| ---- | -------- | ------------------------------------------ |
| 1    | 人物照片 | 必填，正面或轻微侧身，身体不要被大面积遮挡 |
| 2    | 服装图片 | 必填，商品主体清晰，尽量使用纯净背景       |
| 3    | 风格参考 | 可选，用于说明棚拍、街拍或杂志风格         |

用户确认后，系统按配方顺序写入现有源图片列表。若当前工作台已经有图片，必须让用户选择：

- 替换当前源图片；
- 追加到当前源图片；
- 返回调整；
- 取消载入。

### 11.4 提示词与个性化要求

- 默认提示词必须对用户可见、可复制、可编辑。
- P0 不使用对用户完全隐藏的提示词后缀。
- 配方可以定义 `replace` 或 `append` 建议，但应用前必须让用户确认。
- 如果工作台已有非空 prompt，必须弹出项目 Dialog，允许“替换”“追加”“保留当前内容并取消应用”。
- 专题可以提供一个“个性化要求”输入框，例如颜色、背景、风格或保留元素；该内容只能按固定规则追加，不能执行模板代码。
- 后台可以使用受限占位符，例如 `{{user_instruction}}`，但解析器只接受已登记变量，不支持表达式、函数或网络访问。

### 11.5 模型与供应商兼容

配方优先声明能力要求：

```ts
type ShowcaseCapabilityRequirements = {
    supportsEditing?: boolean;
    supportsMask?: boolean;
    supportsCustomSize?: boolean;
    minReferenceImages?: number;
    supportedTaskModes?: Array<'image-generate' | 'image-edit'>;
};
```

应用规则：

1. 当前用户已选择的模型满足要求时，保留当前模型和供应商实例。
2. 当前模型不满足时，在用户已配置、已启用的模型中推荐兼容项。
3. 没有兼容模型时，显示“需要支持图片编辑 / 多参考图的模型”，并提供进入现有供应商设置的入口。
4. 配方可以配置 `preferredModelIds` 作为经过验证的优选项，但不能强制用户切换到尚未配置的供应商。
5. 配方不得携带或写入 API Key、Base URL 和代理配置。
6. 自定义模型能力未知时按保守策略处理，不静默假设支持。
7. 若配方版本高于客户端支持版本，可以继续展示案例，但禁用“载入工作台”，并提示升级应用或手动使用提示词。

### 11.6 参数应用

P0 允许配方设置以下白名单字段：

- `taskMode`；
- `prompt` / `promptStrategy`；
- `n`；
- `scenarioId` 或标准 `size`；
- `customWidth` / `customHeight`，仅在模型支持时；
- `quality`；
- `outputFormat`；
- `outputCompression`；
- `background`；
- `moderation`；
- 输入槽位与源图片顺序；
- 可选的模型能力要求和优选模型列表。

不允许直接设置：

- API Key、Base URL、代理和服务器密码；
- 任意 provider raw JSON；
- 云同步、分享、历史和工作空间配置；
- 自动提交开关；
- 本地路径和任意远程下载地址；
- 未在客户端白名单中登记的新字段。

### 11.7 载入结果

配方成功应用后：

- 自动滚动并聚焦到工作台编辑区；
- 显示“已载入：专题 / 案例”的 Notice；
- 在表单内显示可关闭的来源 Chip；
- 用户仍可修改 prompt、图片、模型和全部参数；
- 生成按钮由用户主动点击；
- 提交任务时附加可选归因元数据：`topicId`、`caseId`、`recipeVersion`、`catalogRevision`；
- 清除来源 Chip 只移除归因，不自动清空用户已经修改的表单。

## 12. 默认专题规划

### 12.1 首发要求

P0 至少内置 6 个高质量专题、每个专题至少 3 个案例，总案例数不少于 24 个。以下三个专题为必选：

1. 老照片修复；
2. 虚拟试衣间；
3. 创意风格化。

默认专题必须同时提供简体中文和英文内容，并包含经过项目实际模型流程验证的配方。不能只生成漂亮封面而没有可用的工作台配置。

### 12.2 推荐首发目录

| 专题                   | 主要任务模式     | 输入要求                 | 建议案例                                   | 关键说明                                             |
| ---------------------- | ---------------- | ------------------------ | ------------------------------------------ | ---------------------------------------------------- |
| 老照片修复             | 图片编辑         | 1 张老照片               | 去划痕、褪色修复、清晰增强、自然上色       | 强调身份和年代细节可能被 AI 推断，结果需人工核对     |
| 虚拟试衣间             | 多参考图编辑     | 人物图 + 服装图          | 上衣、外套、礼服、街拍造型                 | 不承诺真实尺码、面料垂坠和购买效果；需要明确图片顺序 |
| 创意风格化             | 图片编辑         | 1 张主体图               | 水彩、动画、黏土、电影海报、水墨、像素艺术 | 可复用现有默认提示词模板，但增加输入与兼容信息       |
| 电商商品场景图         | 图片编辑         | 1 张商品图，可选品牌参考 | 白底主图、生活场景、节日促销、材质特写     | 要求保留商品结构、Logo 和关键文字，提示可能失真      |
| 图片清晰增强与背景清理 | 图片编辑         | 1 张图片                 | 清晰增强、去杂物、重绘背景、光线优化       | 与“老照片修复”区分现代照片和商业图片场景             |
| 人像头像与形象照       | 图片编辑或文生图 | 1 张人像，可选风格参考   | 职业头像、社交头像、杂志人像、证件感照片   | 明确身份一致性和正式证件用途限制                     |

### 12.3 后续候选专题

- 室内空间换风格；
- 美食与菜单视觉；
- 社交媒体封面与知识卡片；
- 品牌海报与活动 KV；
- 儿童涂鸦转插画；
- 线稿上色与漫画化；
- 旅行照片氛围重塑；
- 节日营销素材；
- 商品模特与配饰搭配；
- 批量图片统一风格。

新增专题优先依据用户任务数据、专题转化和真实案例质量，而不是按模型发布数量无限扩张。

## 13. 后台管理需求

### 13.1 导航与权限

在现有 Admin Shell 增加 `/admin/showcases` 导航，建议用户可见名称为“专题案例”。权限沿用现有规则：

| 操作                           | owner | admin        | viewer |
| ------------------------------ | ----- | ------------ | ------ |
| 查看专题、案例、发布记录和指标 | 允许  | 允许         | 允许   |
| 创建、编辑、复制、排序         | 允许  | 允许         | 禁止   |
| 上传或登记媒体                 | 允许  | 允许         | 禁止   |
| 发布、下线、归档、回滚         | 允许  | 允许         | 禁止   |
| 永久清理已归档内容或媒体       | 允许  | 可按策略限制 | 禁止   |
| 查看审计记录                   | 允许  | 允许         | 允许   |

所有写操作必须通过现有 `requireAdminApi`、来源校验和审计机制，不另建管理员 Token。

### 13.2 专题列表

列表支持：

- 搜索标题、slug、标签；
- 按草稿、待发布、已发布、已下线、已归档筛选；
- 按分类、语言完整度、发布时间筛选；
- 拖拽或数值调整推荐排序；
- 快速启停首页推荐；
- 显示案例数、缺失字段、当前发布版本和最近修改人；
- 复制专题；
- 预览草稿；
- 发布、下线和归档。

### 13.3 专题编辑器

专题编辑器包含：

- 基础信息：内部名称、slug、分类、标签、推荐状态、排序；
- 多语言：标题、摘要、介绍、准备要求、适用范围、限制、FAQ、SEO 字段；
- 封面与缩略图；
- 案例列表和排序；
- 相关专题；
- 可见时间：`startsAt` / `endsAt`；
- 展示范围：Web、桌面、移动端，可默认全端；
- 发布校验结果；
- 桌面/移动、浅色/深色预览。

slug 发布后默认保持稳定。修改 slug 时必须生成兼容别名或明确提醒旧链接失效风险。

### 13.4 案例编辑器

案例编辑器包含：

- 案例标题、摘要、效果解释；
- 输入与输出媒体；
- 前后对比方式；
- 输入槽位编辑；
- 默认 prompt 与个性化要求；
- 任务模式；
- 模型能力要求；
- 推荐模型；
- 场景尺寸与输出参数；
- 注意事项；
- 配方 JSON 只读预览；
- 校验结果；
- “在真实工作台中预览载入”操作。

后台首选结构化表单，不把原始 JSON 作为日常编辑入口。高级 JSON 仅用于诊断或导入导出，并必须经过同一 schema 校验。

### 13.5 媒体管理

案例媒体来源支持：

- 应用随包内置的静态资产；
- 已验证的公开 HTTPS 图片 URL；
- 自托管本地媒体存储；
- 单独配置的服务端 S3 兼容媒体存储。

不得复用普通用户在客户端配置的 S3 同步密钥作为后台媒体存储凭证。

媒体上传要求：

- 校验 MIME、扩展名、像素、文件大小和可解码性；
- 清理 EXIF 中的定位和无关隐私信息；
- 生成缩略图和响应式尺寸；
- 记录版权来源、授权说明和替代文本；
- 不允许 SVG 脚本或未经清洗的富媒体；
- 删除媒体前检查发布版本和案例引用；
- 多实例或 Serverless 部署不得依赖临时本地磁盘作为唯一持久存储。

P0 若尚未实现服务端上传，至少支持“内置资产 + 安全 HTTPS URL”，并把服务端上传明确列为上线前运维选项，而不是让管理员填写任意私网地址。

### 13.6 草稿、预览与发布

内容状态建议：

```text
draft → scheduled → published → unpublished → archived
```

规则：

- 草稿可以持续编辑，不影响当前线上版本；
- 预览只对已登录管理员开放，或使用短时、单用途预览 Token；
- 发布时创建不可变发布快照，专题和案例同时切换；
- 发布校验失败时不修改线上版本；
- 定时发布由服务端时间执行；
- 下线后公开 API 不再返回，但旧任务历史中的归因字段仍保留；
- 归档默认为软删除；
- 至少保留最近 10 个发布版本或 90 天版本历史；
- 支持回滚到一个仍兼容的历史发布版本；
- 发布、下线、回滚和永久清理必须写审计日志。

### 13.7 发布前校验

专题发布必须满足：

- slug 合法且唯一；
- 简体中文和英文必填字段完整；
- 至少一个启用案例；
- 首页推荐专题有封面；
- 每个案例有输入和输出示例、alt、配方和输入说明；
- 所有配方通过 schema、字段白名单和模型能力校验；
- 所有媒体可访问或已存储；
- 不包含密钥、私网 URL、用户本地路径和超大内联数据；
- 富文本经过白名单清洗；
- 时间窗有效；
- 配方版本被当前最低支持客户端理解；
- 关联专题不存在循环导致的无限导航。

## 14. 数据模型建议

### 14.1 设计选择

不建议把专题直接扩展为 `promo_configs` / `promo_items`：

- Promo 当前以 slot、scope、展示比例、约束、时间和轮播素材为中心（`src/lib/server/schema.ts:165-223`）；
- 公共 Placement 只表达展示位和轮播项；
- 专题需要正文、多语言、案例、输入槽位、配方版本和发布快照；
- 把复杂内容塞进 `promo_items` 会让投放、内容、执行和版本管理耦合。

建议新增独立表，并通过稳定 ID 与 Promo 或短链引用。

### 14.2 建议实体

```ts
type ShowcaseTopicStatus = 'draft' | 'scheduled' | 'published' | 'unpublished' | 'archived';

type ShowcaseTopicRecord = {
    id: string;
    slug: string;
    status: ShowcaseTopicStatus;
    categoryKey: string;
    tagsJson: string;
    featured: boolean;
    sortOrder: number;
    coverAssetId?: string | null;
    startsAt?: number | null;
    endsAt?: number | null;
    publishedRevisionId?: string | null;
    createdByUserId?: string | null;
    updatedByUserId?: string | null;
    createdAt: number;
    updatedAt: number;
};

type ShowcaseTopicLocalizationRecord = {
    topicId: string;
    locale: 'zh-CN' | 'en-US';
    title: string;
    summary: string;
    intro?: string;
    preparation?: string;
    limitations?: string;
    faqJson?: string;
    seoTitle?: string;
    seoDescription?: string;
};

type ShowcaseCaseRecord = {
    id: string;
    topicId: string;
    slug: string;
    enabled: boolean;
    sortOrder: number;
    difficulty: 'beginner' | 'intermediate' | 'advanced';
    recipeJson: string;
    recipeVersion: number;
    createdAt: number;
    updatedAt: number;
};

type ShowcaseCaseLocalizationRecord = {
    caseId: string;
    locale: 'zh-CN' | 'en-US';
    title: string;
    summary: string;
    resultExplanation?: string;
    prompt: string;
    inputGuidanceJson?: string;
    cautionsJson?: string;
```

专题详情可以内联首批案例摘要，案例详情和大图按需加载，避免首页下载完整目录。

### 15.2 公共响应

```ts
type ShowcaseCatalogResponse = {
    schemaVersion: number;
    catalogRevision: string;
    generatedAt: string;
    locale: 'zh-CN' | 'en-US';
    topics: ShowcaseTopicSummary[];

```

要求：

- 只返回已发布且处于有效时间窗的内容；
- 不返回草稿、管理员信息、内部备注、审计内容和存储凭证；
- 未知字段由旧客户端忽略；
- 缺失或非法字段归一化为安全默认值；
- 支持 `ETag` / `If-None-Match`；
- 列表和详情设置可控公共缓存；
- 公开失败不返回内部堆栈和数据库细节；
- CORS 仅允许配置的 Web/Tauri 来源，不能无条件放开管理 API。

### 15.4 三级内容降级

公开读取优先级：

```text
实时远端已发布目录
        ↓ 失败 / 超时 / 不兼容
最近一次成功且校验通过的缓存
        ↓ 不存在 / 损坏
随应用打包的内置默认专题目录
```

要求：

- 最近成功缓存只保存专题 JSON 和小型元数据，不缓存无限数量的大图 Blob；
- 缓存带 `schemaVersion`、`catalogRevision`、时间和校验状态；
- 不兼容的新配方仍可作为只读案例展示；
- 管理端显式下线默认专题只影响成功读取远端目录的客户端；完全离线时允许显示内置默认内容，并标记“离线目录”；
- 返回实时内容后立即替换旧缓存，不需要用户刷新整个应用。

## 16. Web 与 Tauri 边界

### 16.1 Web

- Web 默认读取同源 `/api/showcases`。
- 后台 CRUD、预览和发布只存在于 Web 服务端部署。
- 专题静态页面壳在没有服务端内容时仍可加载内置目录。
- API 故障不能影响工作台加载与提交。

### 16.2 Tauri 桌面与移动端

- 桌面静态包不能依赖本地 Next API 或后台路由。
- 动态专题从可信公共内容服务读取；请求、外链和未来本地文件能力继续通过 `src/lib/desktop-runtime.ts` 等共享封装，不在组件中直接散落 Tauri API。
- 可以短期从现有桌面公共内容来源推导 `/api/showcases`，但建议把当前语义偏窄的 `desktopPromoServiceMode` / `desktopPromoServiceUrl` 逐步泛化为公共内容服务配置。
- 若新增 `desktopPublicContentServiceMode` / `desktopPublicContentServiceUrl`，必须从旧 Promo 配置归一化迁移，不能让现有桌面展示位失效。
- 远端专题服务禁用或不可用时，使用最近成功缓存或内置目录。
- 专题内的内部导航留在应用内；真正的第三方链接使用 `openExternalUrl`。
- Android 不依赖桌面文件路径；图片选择使用系统选择器和现有 WebView 能力。

### 16.3 路由约束

P0 使用静态可导出的 `/topics` 页面壳。任何 Web 专用 SEO 路由都必须有等价的应用内地址，不能把专题核心流程锁定到桌面无法访问的 SSR 动态路由。

## 17. 与现有模块的关系

### 17.1 与 Promo 的关系

Promo 继续负责：

- 展示位；
- 全局或分享 Profile 范围；
- 设备、域名和时间约束；
- 轮播、比例和投放优先级。

专题继续负责：

- 内容解释；
- 案例集合；
- 输入要求；
- 复现配方；
- 发布版本；
- 引导式创作。

集成方式：

- Promo 可以链接到 `/topics?topic=<slug>&case=<caseSlug>`；
- 后续可为 Promo item 增加显式 `actionType: 'external' | 'internal-showcase'`，使 Tauri 能在应用内导航；
- 专题不能通过复制 Promo 数据来管理；
- 专题下线后，相关 Promo 发布校验应提示目标失效。

现有 Promo 公开选择顺序为 share → global → legacy（`src/lib/server/promo/public.ts:388-417`），专题接入不得改变该优先级。

### 17.2 与提示词模板的关系

- 专题案例可以引用或复制默认模板 prompt；
- 提示词模板继续是“快速填词”的轻量工具；
- 专题配方增加输入槽位、能力、参数、说明和版本；
- 管理员修改专题 prompt 不应自动修改用户本地自定义模板；
- 后续可以提供“保存为我的提示词模板”，但不是 P0 必需。

### 17.3 与素材库和灵感库的关系

- 用户可以从资源物料仓库选择专题输入图片；
- 专题公开案例媒体不是用户私有素材，不写入用户素材库，除非用户主动保存；
- 素材灵感库继续管理外部网站入口，不承担专题 CMS；
- 全局功能菜单新增“专题案例”同级入口，不建议把专题隐藏在外部灵感网站列表中。

### 17.4 与场景尺寸的关系

- 配方优先引用稳定 `scenarioId`；
- 客户端按当前模型适配到真实尺寸；
- 场景不存在或当前模型不支持时，回退到安全默认尺寸并向用户说明；
- 后台不重复维护一套与模型注册表脱节的尺寸表。

### 17.5 与分享和短链的关系

- 专题和案例使用不含密钥的公开 URL，可以交给现有短链体系缩短；
- 专题链接不应复用带 API Key 的普通分享参数；
- 后续可以在分享工作台配置时附带 `topicId` / `caseId` 归因，但接收者仍使用自己的配置；
- 旧短链即使指向历史发布版本，也应至少能打开专题并提示案例已更新或下线。

## 18. 指标与数据反馈

### 18.1 漏斗事件

建议记录：

| 事件                          | 触发点                       | 关键匿名字段                     |
| ----------------------------- | ---------------------------- | -------------------------------- |
| `showcase_impression`         | 专题卡进入视口               | topicId、位置、目录版本、runtime |
| `showcase_open`               | 打开专题                     | topicId、入口、runtime           |
| `showcase_case_open`          | 查看案例                     | topicId、caseId                  |
| `showcase_recipe_prepare`     | 开始准备输入                 | topicId、caseId                  |
| `showcase_recipe_apply`       | 配方成功载入工作台           | topicId、caseId、recipeVersion   |
| `showcase_generation_submit`  | 用户主动提交来源于案例的任务 | topicId、caseId、modelId         |
| `showcase_generation_success` | 对应任务成功                 | topicId、caseId、modelId         |
| `showcase_generation_failure` | 对应任务失败                 | topicId、caseId、标准化错误类别  |

不得记录：

- 用户图片、图片哈希或本地路径；
- 完整 prompt 或个性化要求；
- API Key、Base URL、密码和 Token；
- 未经隐私评估的 IP、设备指纹或跨站标识。

### 18.2 关键指标

上线前先建立基线，上线后重点看：

- 首页专题曝光 → 专题打开率；
- 专题打开 → 案例打开率；
- 案例打开 → 开始准备率；
- 开始准备 → 配方载入率；
- 配方载入 → 真实提交率；
- 提交 → 成功率；
- 各专题的配置缺失率和模型不兼容率；
- 用户从专题进入后修改 prompt、图片或参数的比例；
- 新用户首次成功生成耗时；
- 专题来源任务的 7 日再次使用率。

### 18.3 初始体验目标

在正式放量前进行至少 5 名非专业用户的可用性测试，目标为：

- 至少 4/5 能在 30 秒内指出三个可用能力；
- 至少 4/5 能在 60 秒内选中案例并进入输入准备；
- 至少 4/5 能说明系统尚未自动提交、仍需自己点击生成；
- 至少 4/5 能区分“人物图”和“服装图”等多输入角色；
- 任何受试者都不应误以为载入案例会替换其 API Key 或自动收费。

## 19. 安全、隐私与内容可信

### 19.1 配方安全

- 配方只接受版本化 schema 和白名单字段；
- 所有未知字段忽略或拒绝，不透传给供应商；
- 配方内容按普通数据处理，不执行脚本；
- rich text 使用严格允许列表，不允许内联事件、iframe 和危险 URL；
- 公开配方中发现密钥模式、私网 URL 或本地路径时阻止发布；
- 所有外部 URL 复用或加强项目现有公共 URL 安全校验，不扩展到 localhost、私有 IP 或带凭证 URL。

### 19.2 用户图片与隐私

- 用户图片只进入现有生成/编辑流程，不上传到专题 CMS；
- 引导步骤退出后及时释放未使用的对象 URL；
- 不为分析事件上传缩略图或图片内容；
- 专题案例不得鼓励用户上传身份证、医疗影像、裸露未成年人等高风险内容；
- 涉及真实人物时提示用户确认拥有处理和上传图片的权利。

### 19.3 案例真实性

- 案例结果必须来自实际可运行流程，记录模型、配方版本和生成日期供内部审计；
- 对公开用户可以隐藏内部供应商凭证，但不能虚构输入条件；
- 示例允许挑选较好结果，但应说明“结果会因模型、输入质量和随机性不同”；
- 前后图片使用一致裁剪和合理压缩；
- 对多次生成后挑选结果的案例，内部记录候选数量；
- 禁止将手工重度后期结果冒充单次自动生成。

### 19.4 专题专项提示

- 老照片修复：AI 可能重建不存在的面部、服饰和背景细节，不能用于历史证据鉴定。
- 虚拟试衣：不保证尺码、剪裁、面料、颜色和实际购买效果，不把结果描述为真实试穿证明。
- 人像与头像：身份一致性可能变化；正式证件、金融验证等场景不得依赖生成图。
- 商品图：Logo、标签、文字和商品结构可能失真，发布前必须人工核对。

## 20. 性能与稳定性

### 20.1 前端性能

- 首页摘要接口 gzip 后建议控制在 200 KB 内；
- 首页一次最多渲染 8 个专题卡片；
- 封面使用响应式 WebP/AVIF/JPEG，不直接加载原始大图；
- 详情首屏只加载当前专题和首批案例，更多案例按需加载；
- 前后对比原图仅在组件进入视口时加载；
- 专题请求不加入工作台首屏阻塞链；
- 不在首次渲染扫描历史、IndexedDB Blob 或完整目录；
- 远端请求设置超时、取消和并发上限；
- 离开专题详情后取消未完成请求。

### 20.2 服务端性能

- 公开接口只查询已发布快照，不在每次请求拼接全部草稿表；
- 发布时生成快照和内容 hash，读取路径保持轻量；
- 列表使用索引覆盖 `status`、`featured`、`sortOrder`、时间窗；
- 详情按 slug 和当前 revision 定位；
- 指标采用异步聚合，不阻塞案例打开和配方应用；
- 不对每次公开读取执行外部图片可用性探测。

### 20.3 故障隔离

- 专题 API 500、超时、返回非法 JSON 或媒体失败时，工作台仍可正常生成和编辑；
- 单个非法专题不能让整个目录不可用；
- 单个非法案例从公开结果中隔离，并在后台显示发布诊断；
- 缓存损坏时删除该缓存并回退内置目录；
- 远端内容服务恢复后可自动更新，不要求重启桌面应用。

## 21. 国际化、主题与可访问性

### 21.1 国际化

项目当前支持 `zh-CN` 和 `en-US`（`src/lib/i18n/language.ts:1-15`）。要求：

- 产品固定 UI 文案进入 `src/lib/i18n/*`；
- 后台内容分别维护简体中文和英文；
- 发布前校验两种语言的必填字段；
- 分类和标签优先使用稳定 key，由客户端翻译；
- 模型名、技术 ID 和用户数据使用 `data-i18n-skip`；
- 缺失当前语言时可以回退默认语言，但必须标记后台缺失，不能长期静默混用。

### 21.2 主题和布局

- 使用 `app-theme-scope`、`app-panel-card`、`app-panel-subtle` 和 CSS 变量；
- 避免硬编码纯白/纯黑；
- 专题卡、详情、引导、后台预览都验证浅色和深色主题；
- 390×844 等移动视口无横向溢出；
- 桌面在 1280、1440 宽度下内容不拥挤；
- 文本截断不遮挡输入要求和主要按钮；
- 适配 safe-area inset。

### 21.3 可访问性

- 卡片、对比控件、步骤和 Dialog 可键盘操作；
- 前后对比滑杆有可读 label、当前值和方向键支持；
- 图片提供有意义 alt；
- 不用颜色作为唯一状态表达；
- 动画遵循 `prefers-reduced-motion`；
- 加载、错误、配方应用结果通过适当的 live region 或 Notice 告知；
- 触摸目标不小于项目现有按钮规范；
- 焦点在 Dialog 打开、关闭和步骤切换时可预测地移动。

## 26. 主要风险与缓解

| 风险                          | 影响                   | 缓解                                                           |
| ----------------------------- | ---------------------- | -------------------------------------------------------------- |
| 案例很好看但难复现            | 用户信任下降           | 只发布实际跑通案例，记录配方版本、模型和候选次数，明确结果差异 |
| 专题变成第二套复杂工作台      | 新手仍然困惑           | 引导只展示当前案例必需步骤，高级参数最后再进入现有工作台       |
| 配方绑定单一供应商            | 用户配置不同就无法使用 | 以能力为主、模型 ID 为推荐，保留当前兼容模型                   |
| 多图顺序不清楚                | 试衣等结果错误         | 输入槽位角色化、示意图、排序预览和提交前校验                   |
| 后台半成品泄漏线上            | 公开内容残缺           | 草稿与不可变发布快照分离，发布原子切换                         |
| 专题远端服务影响主工具        | 首页卡顿或不可用       | 延迟加载、超时、缓存、内置回退和故障隔离                       |
| 默认专题数量过多              | 内容质量和维护失控     | 首发 6 个专题，按数据扩展，不按模型数量扩展                    |
| 案例图片版权不清              | 法律和品牌风险         | 媒体记录来源和授权，发布前审核，支持快速下线                   |
| 用户误认为结果保证            | 投诉与误用             | 显示模型、输入和随机性说明，专项用途限制                       |
| 动态 slug 与桌面静态导出冲突  | Tauri 无法访问新专题   | 使用静态 `/topics` 页面壳和远端 JSON，SEO 路由独立增强         |
| 将内容塞入 Promo 导致模型失控 | 后台和 API 难以维护    | 专题独立领域，Promo 只保存导流关系                             |
| 配方扩展成为任意 JSON         | 安全与兼容风险         | 版本化 schema、字段白名单、管理员结构化编辑器                  |

## 28. 完成定义

本需求的完成不是“页面上出现专题卡片”，而是形成完整闭环：

1. 用户能发现专题；
2. 用户能理解案例；
3. 用户能准备正确输入；
4. 系统能校验模型和参数；
5. 配方能透明、安全地载入现有工作台；
6. 用户主动生成并在历史中继续复用；
7. 管理员能独立维护和发布内容；
8. Web、桌面和移动端都能工作或清晰降级；
9. 远端专题故障不会伤害专业工具主流程；
10. 团队可以通过漏斗数据判断专题是否真正降低了上手门槛。

## 30. v2.15.10 发现体验与分析可靠性增量

> 2026-08-04 第七次实现核对。该增量已完成专题发现、案例理解、配置可用性提示、匿名事件可靠性和后台登录态验收；总体结论仍为 **部分完成 (Partial)**，因为默认 24 个真实案例资产、5 名非专业用户测试、分析多实例集中存储以及桌面/Android 安装级验收仍未完成。

### 30.1 用户发现与快速理解

- 专题中心支持关键词、输入类型、能力标签和双语任务分类筛选；关键词输入会立即更新结果，300ms 防抖后同步到可分享 URL，按 Enter 可立即同步。
- 搜索输入草稿会参与后续输入类型、能力标签、任务分类和排序变更，避免快速组合操作丢失关键词；输入后直接进入专题不会被延迟 URL 更新拉回目录，重置会同时清空结果和 URL。
- 提供推荐优先、最近更新和新手友好三种排序；`publishedAt` 由服务端发布记录或内置目录生成，旧 v1 客户端不会收到扩展字段。
- 专题卡展示无需图片、固定图片数或图片数范围，并根据当前模型、凭据和兼容模型给出可用、可切换、需配置或仅查看状态；配置、表单偏好、跨页恢复和跨标签存储变化会触发重新计算。
- 当专题仅包含客户端未知 recipe 时，卡片显示“输入要求未知”，输入类型筛选会排除该专题，不会把合成的空 recipe 当成“无需图片”；当前表单选中的非默认供应商实例凭据也参与可用性判断。
- 案例卡展示输入槽位的角色与顺序；详情页提供默认提示词复制与失败反馈；紧凑卡提供触摸和键盘可操作的前后对比切换。
- 目录与案例只负责准备和解释配方，进入工作台的 deep-link 仍不携带自动提交字段。

### 30.2 后台运营与兼容契约

- 后台结构化编辑器新增双语任务分类字段，支持扩展字段的客户端可据此筛选；严格 v1 响应移除 `categories` 和 `publishedAt`。
- 支持扩展字段的客户端通过 `x-showcase-client-version: 2` 声明扩展 wire 契约；这不是 catalog schema v2。旧客户端仍获得只包含可执行 v1 案例的原子目录，未来 recipe 不会拖垮其他案例。
- 后台可导出最近 30 天匿名事件 NDJSON，并记录导出审计；导出有时间窗和 50,000 行上限，不包含请求元数据、用户标识、prompt 或媒体内容。

### 30.3 匿名事件可靠性

- 浏览器端使用最多 100 条、最长 7 天的有界 localStorage 队列；单批最多 25 条。
- 网络错误和非 2xx 响应会回队，并按 1 秒、5 秒、30 秒、2 分钟、5 分钟的有限退避重试。
- `pagehide` 与页面隐藏时优先使用 `sendBeacon`；不可用或返回失败时回退到 `fetch keepalive`，发送仍失败才回队；生命周期监听可清理，避免热更新或测试累计重复监听。
- 曝光以“目录版本 + 专题”为会话去重键，不因排序或位置变化重复计数。
- 队列恢复继续经过事件白名单归一化，未知字段、过期事件和包含 prompt 等敏感扩展的事件会被丢弃。
- 首次发送失败按 1 秒档重试；调度器直接等待最早的 `nextAttemptAt`，不会在长退避期间以 750ms 空轮询。
